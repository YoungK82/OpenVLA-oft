**2026-09-28 trajectory-check 실행 분석**

대상은 `EVAL-SO101-2026_09_28-20_15_08--trajectory-check.txt`와 같은 이름의 MOTOR-FEEDBACK CSV다. 사용자 확인: 실제 화면에서 front=0, top=1, wrist=2가 맞다. 카메라 번호가 뒤바뀌었다는 가설을 현재 원인으로 삼지 않는다.

**확인된 결과**

- `dry_run=False`, step 0~1799가 누락 없이 기록됐다. CSV도 1800 step × 6개 motor = 10,800행이다. 이번 파일은 90-step 실행이 아니라 1800-step 실행이다.
- 첫/마지막 피드백 timestamp 차이는 86.035초다. 총 query_time은 25.061초이고 일반 step 간격 중앙값은 33.821ms다. 긴 간격은 30-step 주기로 나타나므로 동기 추론 대기가 포함된 동작과 부합한다.
- 모든 predicted 및 safe 값은 유한하다. 로그 끝은 정상 episode 요약이며 `success=False`는 운영자가 입력한 평가 결과다.
- CSV의 errors 필드는 모두 비어 있다. 모터 오류가 기록됐다는 증거는 없지만, 빈 필드만으로 하드웨어 정상이나 과부하 부재를 확정할 수 없다.

팔 관절은 기존 데이터의 degree 단위이고 gripper는 별도 단위다. 학습 범위는 경험적 데이터 범위이며 기계적 한계가 아니다. `safe`는 클라이언트가 제한한 목표이며, 실제 위치나 LeRobot 내부 제한을 거친 최종 명령이라는 뜻이 아니다.

**가장 눈에 띄는 문제는 gripper 목표가 전 구간에서 0 부근에 머무른다는 점이다.** 체크포인트의 학습 action 범위는 gripper 0~53.672이고, 이번 최대 목표는 1.048이다. 1800개 목표 중 421개는 학습 최소값 0보다 작다. 기존 calibration에서 0 부근이 닫힘에 대응한다면, 열어서 접근하고 집는 동작에 필요한 목표를 거의 생성하지 않은 셈이다. 실제 그리퍼 위치는 이 CSV로 확인할 수 없다.

팔 목표도 고정된 상태가 아니다. 첫 150 step의 shoulder_lift 평균 목표는 -82.320이고 step 600~749에서는 -17.703까지 이동했다가 마지막 150 step에서는 -58.822로 돌아간다. elbow_flex도 같은 구간에서 평균 82.666 → 9.593 → 63.070으로 크게 변한다. 이는 모델이 생성한 관절 목표 변화이며, 실제 손끝의 공간 경로나 로봇이 따라간 경로를 뜻하지 않는다.

모든 관절을 합쳐 제한이 적용된 step은 9/1800개(0.5%)다. 따라서 이 로그의 클라이언트 제한이 전 구간을 막아서 진행하지 못했다고 보기는 어렵다. 단, 로봇 API 내부 제한이나 하드웨어의 추종 실패 여부는 아직 모른다.

**현재 자료로 특정할 수 없는 원인**

CSV에는 `current_A`, `load_pct`, `errors`, `torque_est_Nm`만 있고 measured joint position이 없다. TXT에도 observation state, 전체 설정, 서버 request_id, send_action 반환값이 없다. 따라서 다음을 직접 계산할 수 없다.

- 모델 입력 state가 학습 proprio 범위와 맞았는지, calibration/단위가 바뀌었는지.
- 모델 목표와 실제 위치의 추종 오차 및 LeRobot 내부 제한.
- 이미지의 장면·전처리가 학습 때와 일치하는지, 그리퍼가 실제로 열리거나 닫혔는지.

현재 근거는 모델의 그리퍼 목표 생성과 큰 팔 목표 변화에 대한 추가 조사가 필요하다는 것이다. 카메라 순서, calibration, 전처리, 모델 정책 품질 중 하나를 확정 원인으로 지목할 단계는 아니다. 변화량 제한을 높이거나 실행시간을 더 늘리는 것으로 원인이 해결된다고 볼 근거도 없다.
