**실제 Windows 코드 확인**

- `so101_utils.py`는 서버 저장소 파일과 동일하다. 입력 순서는 front → top → wrist, 관절 순서도 동일하고 `use_degrees=True`다.
- `vla_client_utils.py`는 기능상 HTTP timeout이 30초에서 300초로 늘어난 것이 주요 차이다. JPEG/resize와 JSON 처리는 동일하다.
- 매 step `get_observation()`을 호출하고, queue가 비면 관측으로 새 요청을 만든다. 받은 action은 `popleft()`로 순서대로 소모한다. 업로드 코드에서 동일 chunk를 반복 재생하는 분기나 top/wrist 순서를 뒤집는 코드는 발견하지 못했다.
- query에 사용한 관측의 state를 응답 후에도 client 제한에 사용한다. 따라서 query step에서는 약 0.44초 전 state로 제한을 계산할 수 있다. 이는 확인된 지연 특성이나, 이번 궤적의 원인이라고 확정할 수 없다.
- state, 실제 send_action 반환값, 전체 실행 설정, request_id가 저장되지 않는다. 모터 CSV는 위치가 아니라 전류/부하를 저장한다. `MotorFeedbackLogger` 구현인 `motor_feedback.py`는 전송되지 않았다.
- 영상은 front 뷰를 step당 한 장씩 모아 고정 30fps로 저장한다. 1800 frame이면 약 60초 재생이며 실제 실행 87.49초의 요청 대기시간을 그대로 재현하지 않는다.

CSV의 errors 필드는 모두 비어 있다. 현재 기록만으로 모터 과부하·추종 실패·calibration 오차를 판정할 수 없다. torque_est_Nm도 코드에 명시된 미보정 추정값이다.

**현재 결론과 다음 자료**

연결 실패나 동일 chunk의 단순 반복 재생은 현재 증거로 지지되지 않는다. 정상 매핑에서도 그리퍼 목표가 하단에 머물고 팔 목표가 넓게 움직이며, 일부 목표가 제한되는 현상은 확인됐다. 모델이 현재 장면/상태에서 잘못된 목표를 생성하는지, 로봇이 목표를 추종하지 못하는지를 구분하려면 대응 영상과 측정 state가 필요하다.
