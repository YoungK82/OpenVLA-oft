# OpenVLA-OFT on a Real-World SO-101 Robot

This guide follows the same data → RLDS → fine-tuning → server/client evaluation flow as `ALOHA.md`, adapted to
LeRobotDataset v3 and the single-arm SO-101. The ALOHA implementation is the reference integration; training starts
from OpenVLA-7B, not from an ALOHA task checkpoint. Example commands below are distinct from the completed trimmed
experiment documented at the end of this guide.

## Relevant Files

Training:

* `experiments/robot/so101/convert_lerobot_to_rlds.py`: converts a local LeRobotDataset v3 recording to RLDS
* `experiments/robot/so101/verify_rlds_dataset.py`: verifies images, 6D state/action, splits, and action statistics
* `experiments/robot/so101/smoke_test_server.py`: sends a real validation sample through a deployed checkpoint
* `vla-scripts/finetune.py`: shared OpenVLA-OFT LoRA fine-tuning entry point
* `SO101_INFERENCE_SMOKE_TEST.md`: Kubernetes runbook for loading a smoke checkpoint and testing one RLDS request

Evaluation:

* `vla-scripts/deploy.py`: GPU-side VLA inference server
* `experiments/robot/so101/run_so101_eval.py`: SO-101-side client and control loop
* `experiments/robot/so101/so101_utils.py`: ordered observation conversion and action safety checks

The training and robot-client environments should be separate. The robot machine only needs enough compute to read
cameras, communicate with the SO-101, and call the VLA server.

## Data Contract

This pipeline intentionally fixes one contract from recording through deployment:

```text
images:  front → top → wrist
state:   shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper
action:  absolute positions for the same six joints
rate:    30 Hz
chunk:   30 actions (one second)
```

Camera device indices are not camera identities. Verify the physical views before each session: the latest confirmed
Windows mapping was `front=2`, `top=1`, `wrist=0`, while the semantic model order remains front → top → wrist.
The `0/1/2` indices in the example commands are placeholders, not a required physical mapping.

Use the same SO-101 `id` and calibration when recording and evaluating. Changing calibration changes the meaning of
the absolute joint values.
Arm joints use degrees in this client; the gripper convention must be checked separately against the recorded data
and LeRobot configuration. Do not interpret every component of a six-dimensional action as an angle in degrees.
Dataset normalization/unnormalization and the relative-target command limit are separate operations.

### Why three cameras, and how this differs from ALOHA

OpenVLA-OFT does not automatically consume every camera physically attached to a robot. The ALOHA recipe in this
repository explicitly trains with three images: one third-person image, one left-wrist image, and one right-wrist
image. It does not feed six images to the policy. SO-101 follows the same three-image model interface, but maps it to
one front image, one top image, and one wrist image.

The order is part of the learned model contract, not cosmetic metadata:

| Model image index | ALOHA | SO-101 |
| --- | --- | --- |
| 0 | third-person | front |
| 1 | left wrist | top |
| 2 | right wrist | wrist |

### Why RLDS alone is not enough

Any4LeRobot can perform the mechanical LeRobot-to-RLDS conversion, but RLDS only defines the dataset container. An
OpenVLA-OFT dataset must additionally agree with this repository on field names, camera order, state/action semantics,
normalization, action dimension, action chunk length, language labels, and train/validation splits. The current
Any4LeRobot converter creates only a `train` split and dynamically preserves source field names, so its output is not a
drop-in replacement for this SO-101 pipeline.

The SO-101 converter is intentionally narrower: it rejects incompatible joint order, missing cameras, missing language,
short episodes, and an unexpected recording rate before writing the exact schema registered in OpenVLA-OFT. Producing
an RLDS directory successfully does not by itself prove that a trained policy will produce meaningful robot actions.

## What Was Broken and What Changed

| Boundary | Earlier problem | Current fix |
| --- | --- | --- |
| Robot constants | Tensor dimensions were inferred from loose command-line substring matching and could silently fall back to LIBERO | Added explicit `--robot_platform so101` and fixed SO-101 constants: 30-step chunk, 6D action, 6D proprio |
| LeRobot to RLDS | Conversion did not enforce FPS, episode length, language, deterministic validation split, or record the conversion contract | Added source validation, a train/validation episode split, and `so101_conversion_manifest.json` |
| RLDS to OpenVLA | A generic multi-camera path did not make the SO-101 camera meaning and order obvious | Registered `image`, `top_image`, and `wrist_image` as primary, secondary, and wrist; batch assembly uses that exact order |
| Fine-tuning | `finetune.py` had no SO-101-specific fail-fast check | It now validates the first real batch as 18 transformed image channels, 6D proprio, and `[batch, 30, 6]` actions |
| Inference input | Additional images were discovered from dictionary key names, which could omit `top` or change ordering | Robot clients now send an ordered `additional_images` list, giving front, top, wrist at inference exactly as in training |
| Inference output | There was no SO-101 checkpoint-to-robot path | Added action unnormalization, `[30, 6]` validation, named-joint conversion, non-finite rejection, relative-target limiting, and dry-run-first evaluation |
| Verification | Static shape assumptions were not exercised end to end | Added staged RLDS, GPU training, and deployed-checkpoint smoke tests below |

## Setup

Create the GPU training environment using `SETUP.md`. On the computer connected to the SO-101, create a separate
environment. `requirements_so101.txt` pins `lerobot>=0.6.0`, which requires **Python 3.12+**:

```bash
conda create -n openvla-oft-so101 python=3.12 -y
conda activate openvla-oft-so101

pip install -r experiments/robot/so101/requirements_so101.txt
```

Do not `pip install -e .` (the repo root `pyproject.toml`) into this environment. That installs the GPU
training/inference stack, which pins `tensorflow==2.15.0` — a version with no Python 3.12 wheel — so it cannot
coexist with `lerobot>=0.6.0` in one environment. The robot client does not need it: `so101_utils.py` and
`run_so101_eval.py` now import their two server-facing helpers (`resize_image_for_policy`, `get_action_from_server`)
from `experiments/robot/so101/vla_client_utils.py`, a small standalone module with its own lightweight
`tensorflow`/`requests` dependency instead of pulling in `experiments/robot/openvla_utils.py` (which additionally
imports `torch`, `transformers`, and `prismatic`). Run the client from the `OpenVLA-oft` checkout directory without
installing the package (`sys.path.append(".")` in the scripts makes `experiments.robot.so101.*` importable).

Calibrate and test teleoperation with the official LeRobot SO-101 tools before using a learned policy. Find the serial
and camera devices on the robot machine:

```bash
lerobot-find-port
lerobot-find-cameras opencv
```

## Record SO-101 Demonstrations

Record all three cameras with the exact names used by this pipeline. Adapt ports, ids, and camera indices:

```bash
lerobot-record \
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM0 \
  --robot.id=so101_follower \
  --robot.use_degrees=true \
  --robot.cameras="{ front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}, top: {type: opencv, index_or_path: 1, width: 640, height: 480, fps: 30}, wrist: {type: opencv, index_or_path: 2, width: 640, height: 480, fps: 30}}" \
  --teleop.type=so101_leader \
  --teleop.port=/dev/ttyACM1 \
  --teleop.id=so101_leader \
  --teleop.use_degrees=true \
  --display_data=true \
  --dataset.repo_id=YOUR_HF_USER/so101_block_into_cup_50_v5 \
  --dataset.num_episodes=50 \
  --dataset.single_task="Pick up the block and place it into the cup." \
  --dataset.streaming_encoding=true
```

The converter expects a local LeRobotDataset v3 directory containing `meta/`, `data/`, and `videos/`. If the dataset
was recorded on another machine, download or copy the complete repository first.

## Convert LeRobotDataset v3 to RLDS

```bash
python experiments/robot/so101/convert_lerobot_to_rlds.py \
  --source-root /PATH/TO/LEROBOT/DATASET \
  --output-root /PATH/TO/RLDS/DATASETS \
  --validation-episodes 5 \
  --split-seed 7 \
  --image-size 256
```

The converter refuses data not recorded at 30 Hz because `NUM_ACTIONS_CHUNK=30`. Do not bypass that check without
also changing the SO-101 action chunk and control frequency.

Verify the converted dataset before starting GPU training:

```bash
python experiments/robot/so101/verify_rlds_dataset.py \
  --data-root /PATH/TO/RLDS/DATASETS \
  --dataset-name so101_block_into_cup_50_v5
```

The dataset is registered in `configs.py`, `transforms.py`, and `mixtures.py`, following the same registration pattern
described in `ALOHA.md`. A differently named dataset must be registered in all three files.

## Smoke-Test the Complete Contract

A smoke test proves plumbing, not policy quality. Run all three stages on the supercomputing-center checkout before a
long training job. Do not start the next stage if the previous one fails.

### Stage 1: verify the prepared RLDS dataset

This is a CPU test. It verifies both splits, three decoded images, 6D finite state/action values, language, joint order,
and the conversion manifest:

```bash
python experiments/robot/so101/verify_rlds_dataset.py \
  --data-root /PATH/TO/RLDS/DATASETS \
  --dataset-name so101_block_into_cup_50_v5
```

Inspect the printed state/action ranges. Their unit and calibration must match the evaluation client, which explicitly
uses degrees. A structural pass cannot detect a semantically wrong calibration or a dataset recorded in different
units.

### Stage 2: run a short GPU forward/backward test

Request one GPU using the center's scheduler, activate the OpenVLA-OFT environment, and run:

```bash
WANDB_MODE=offline torchrun --standalone --nnodes 1 --nproc-per-node 1 vla-scripts/finetune.py \
  --robot_platform so101 \
  --vla_path openvla/openvla-7b \
  --data_root_dir /PATH/TO/RLDS/DATASETS \
  --dataset_name so101_block_into_cup_50_v5 \
  --run_root_dir /PATH/TO/RUNS \
  --use_l1_regression True \
  --use_diffusion False \
  --use_film False \
  --num_images_in_input 3 \
  --use_proprio True \
  --batch_size 1 \
  --max_steps 10 \
  --use_val_set True \
  --val_freq 5 \
  --val_time_limit 60 \
  --save_freq 10 \
  --save_latest_checkpoint_only True \
  --merge_lora_during_training True \
  --image_aug True \
  --lora_rank 32 \
  --wandb_entity local \
  --wandb_project so101-smoke-test
```

This stage passes only if the log prints `Validated first training batch`, all losses remain finite, validation runs,
and the checkpoint contains `dataset_statistics.json`, a LoRA adapter, an action head, a proprio projector, and merged
model files. Merging makes the smoke checkpoint directly loadable by `deploy.py`; it is intentionally included even
though it adds a few minutes.

### Stage 3: load the checkpoint and test one real validation observation

Start the server on the allocated GPU using the checkpoint directory produced by Stage 2:

```bash
python vla-scripts/deploy.py \
  --robot_platform so101 \
  --pretrained_checkpoint /PATH/TO/SMOKE/CHECKPOINT \
  --use_l1_regression True \
  --use_diffusion False \
  --use_film False \
  --num_images_in_input 3 \
  --use_proprio True \
  --center_crop True \
  --unnorm_key so101_block_into_cup_50_v5
```

From another shell that can reach that compute node, send a real validation observation through the HTTP server:

```bash
python experiments/robot/so101/smoke_test_server.py \
  --data-root /PATH/TO/RLDS/DATASETS \
  --dataset-name so101_block_into_cup_50_v5 \
  --server-endpoint http://COMPUTE_NODE:8777/act
```

It passes only when the server accepts front/top/wrist images plus 6D state and returns 30 finite, unnormalized 6D
actions. Also inspect the printed first action and its distance from the input state. This catches the complete
dataset-to-checkpoint-to-output contract without connecting a robot.

## Fine-Tune OpenVLA-OFT

After the smoke test passes, launch the real run. Replace `X` with the GPU count and tune batch size to available VRAM:

```bash
torchrun --standalone --nnodes 1 --nproc-per-node X vla-scripts/finetune.py \
  --robot_platform so101 \
  --vla_path openvla/openvla-7b \
  --data_root_dir /PATH/TO/RLDS/DATASETS \
  --dataset_name so101_block_into_cup_50_v5 \
  --run_root_dir /PATH/TO/RUNS \
  --use_l1_regression True \
  --use_diffusion False \
  --use_film False \
  --num_images_in_input 3 \
  --use_proprio True \
  --batch_size 4 \
  --learning_rate 5e-4 \
  --num_steps_before_decay 25000 \
  --max_steps 50005 \
  --use_val_set True \
  --val_freq 5000 \
  --save_freq 5000 \
  --save_latest_checkpoint_only False \
  --image_aug True \
  --lora_rank 32 \
  --wandb_entity YOUR_WANDB_ENTITY \
  --wandb_project YOUR_WANDB_PROJECT \
  --run_id_note so101--30_action_chunk--3_images--proprio--l1
```

The 50K schedule is a starting point, not a claimed optimum. Select checkpoints using validation L1 loss and real
rollouts. This single-task recipe disables FiLM while still passing the language instruction to the model. FiLM is an optional
configuration choice for stronger language grounding, not a feature restricted to multi-task policies.

## Launch the VLA Server

  --use_proprio True \

## Evaluate on the Physical SO-101

The client defaults to `dry_run=True`: it connects, observes, queries the model, validates actions, and logs them without
moving the motors. Start with one open-loop action:

```bash
python experiments/robot/so101/run_so101_eval.py \
  --vla_server_url 192.168.0.10 \
  --robot_port /dev/ttyACM0 \
  --robot_id so101_follower \
  --front_camera 0 \
  --top_camera 1 \
  --wrist_camera 2 \
  --num_open_loop_steps 1 \
  --max_relative_target 5.0 \
  --dry_run True \
  --num_rollouts_planned 1 \
  --max_steps 100
```

Inspect camera order, state values, predicted actions, and logs. Only then enable motor commands:

```bash
python experiments/robot/so101/run_so101_eval.py \
  --vla_server_url 192.168.0.10 \
  --robot_port /dev/ttyACM0 \
  --robot_id so101_follower \
  --front_camera 0 \
  --top_camera 1 \
  --wrist_camera 2 \
  --num_open_loop_steps 1 \
  --max_relative_target 5.0 \
  --dry_run False
```

Keep an emergency stop available and clear people and fragile objects from the workspace. The client rejects malformed
or non-finite actions and limits each joint relative to its measured position. LeRobot applies the same relative-target
limit again before sending the command. Begin with one executed action per model query; increase to at most three only
after repeated safe tests.


## Completed Trimmed SO-101 Experiment

This section records the experiment reported in September 2026. It is not a claim that the generic example commands
above were executed unchanged. The actual training manifest is stored outside this code repository at
`/gpfsai/home/aga/yhkim/openvla-oft/k8s/yhkim-oft-train-trimmed-job-1.yaml` on AIGS.

| Setting | Completed run |
| --- | --- |
| Base model | Local OpenVLA-7B: `/workspace/models/openvla-7b-47a0ec7` |
| Task instruction | `Pick up the block and place it into the cup.` |
| Dataset | `so101_block_into_cup_50_v5/1.1.0` |
| Episode split | 45 training, 5 validation |
| Inputs | Front/top/wrist images, 6D proprio, language |
| Targets | Absolute 6D actions, 30-action chunks |
| Objective | L1 regression; diffusion disabled |
| Adaptation | LoRA rank 32; proprio enabled; FiLM disabled |
| Batch size | 8 |
| Learning rate | Initial `5e-4`, decay after 12,500 steps |
| Training length | 25,000 steps |
| Validation / checkpoint schedule | Every 5,000 steps |
| Image augmentation | Enabled |
| Execution | One NVIDIA H200, AIGS Kubernetes Job |
| Experiment tracking | W&B offline |
| Deployed checkpoint | `so101-b8-s25000-trimmed-job-1--25000_chkpt` |

The training loader constructs action chunks from per-step actions: the current action plus the following 29 actions.
It does not require 30 consecutive observation images per model input. LoRA adapts the base model, and the action head
and proprio projector are also trained. The output head and projector use SO-101 dimensions rather than ALOHA's 14D
configuration.

### Trimming and evidence

The initial policy was observed to repeatedly predict near-stationary poses. Leading stationary segments were analyzed,
and aligned image/state/action steps were removed before regenerating RLDS on the laboratory server. The trimmed
dataset was transferred to AIGS for training. Physical block-into-cup successes were subsequently reported.

This is an observed improvement after retraining, not a controlled demonstration that trimming alone caused the gain.
Archive the onset CSV, exact cut rule, laboratory-side converter version, split membership, and conversion manifest to
reproduce the data preparation. Do not assume the converter in this checkout contains the exact laboratory trimming
procedure. Derive normalization statistics for the dataset actually used, and keep them with its checkpoint.

Structural dataset checks, a completed training run, and finite `[30, 6]` validation-request outputs verify parts of the
pipeline. They do not establish calibration correctness, semantic alignment of every sample, or physical success rate.
The final 25k checkpoint was deployed; it has not been demonstrated to be the best checkpoint across all evaluations.
Validation has a time limit in the shared training configuration, so an individual validation event should not be
assumed to cover every validation frame.

### Deployment and executable-version differences

GPU inference runs in the AIGS Pod `yhkim-openvla-oft-inference-trimmed`; Windows runs the LeRobot camera/robot client.
The inference manifest is `/gpfsai/home/aga/yhkim/yhkim-openvla-oft-inference-trimmed.yaml` on AIGS. These external YAML
files, recordings, and checkpoints are not automatically included when cloning this code repository.

The reported Windows runs used 30 Hz, up to 1,800 action steps, and 30 executed actions per query. However, the client
currently checked into this repository rejects `dry_run=False` with `num_open_loop_steps > 3`. Therefore the Windows
executable differs from this checkout in that validation behavior. Preserve the actual Windows files and their changes
before claiming exact reproducibility. The conservative hardware examples above match the checked-in validation.

`max_steps=1800` at 30 Hz represents 60 seconds of nominal action execution; synchronous model requests add waiting
time. The client does not automatically stop when the task succeeds. `run_id_note` changes the log filename only.
Repeated inference and answering `y` to the success prompt do not update model weights.

### Interpreting command limits and current limitations

The client limits targets relative to its observed state, and LeRobot applies a limit again using a newly read state.
The robot may move between these reads, particularly while waiting for a server response. A LeRobot clamp warning's
original target can therefore already be a client-limited target, rather than the raw model prediction.

The scalar `max_relative_target` applies across the action components in their configured units. It is neither a motor
force setting nor a total joint travel limit. Clamping occurred in both successful and problematic runs. Persistent
clamping, elbow stalls, or gripper oscillation require comparing model targets with measured motion; the warning alone
does not identify the cause. A motor overload is a separate hardware fault, not an ordinary clamp warning.

Observed limitations include gripper opening/closing near grasping, elbow progress stopping at some poses, and
inconsistent progress across action chunks. Their root causes have not been isolated. Before changing limits or adding
smoothing, record:

* The full run configuration, model/checkpoint identity, code version and calibration identity.
* Actual camera-to-device mapping and the three images at query boundaries.
* Joint state before and after each server request.
* Previous final target, new predicted chunk, client-limited targets, and the final command returned by the robot API
  where supported.
* Timing, termination reason, and operator-assessed success.

Existing action logs do not contain all these fields. A success label entered by an operator is not an independently
measured benchmark success rate.

### Planned human-gated DAgger extension

Human intervention collection is not implemented in this SO-101 client. A proposed extension would pause autonomous
execution, discard pending actions and stale inference results, align and hand control to the leader arm, record human
recovery/correction, and resume the policy from a fresh observation. Local takeover handling must remain responsive
while a remote request is pending; the current synchronous request cannot simply block that control path.

Record images, measured state, actions, timestamps, task and human/policy ownership. When converting collected data to
training examples, explicitly choose expert-supervised segments or masks and handle chunk boundaries at handoffs.
Do not indiscriminately treat autonomous failure actions as expert targets. Combine appropriate corrections with
original demonstrations and evaluate the fine-tuned policy under controlled initial conditions. This is a future
improvement plan, not an explanation already proven for the observed failures.
